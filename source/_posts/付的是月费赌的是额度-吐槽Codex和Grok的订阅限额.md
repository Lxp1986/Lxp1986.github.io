先说清楚，我不是嫌贵。

真要算钱，AI 订阅是这个年代性价比最高的东西之一。我一个月掏那点月费，换来的是一个能读我仓库、能替我敲命令、能帮我改脚本的东西，这笔账怎么算都不亏。

我难受的是另一件事：**我交了固定的钱，却买不到固定的量，而且连「今天还能用多少」都算不清楚。**

![订阅制卖的是准入，不是产能：月费是一条直线，可用额度是一条锯齿，随时会被拦停](/img/ai-sub-quota.svg)

## 一、卖准入，不卖产能

订阅制的合同写得很漂亮：解锁完整功能，享受高速推理，高级模型随便用。

但真用起来你会发现，你买的其实是**一张入场券**，不是**一份产能**。

入场之后能跑多少，取决于一堆你事先不知道、事后也未必看得懂的规则：有多大的时间窗、窗里给多少、一周总共给多少、什么任务算重、什么任务算轻、换了个模型算不算重算。

这就很荒诞。我付的是「一个月」，拿到的是「一个不确定的窗口」。

修一个 bug，顺利的时候两轮搞定；不顺利的时候，跟同一段报错来回拉扯，额度就跟漏气一样往下掉。

这不是我凭感觉说的。我把自己 43 天、6880 个采样点的 Codex 额度日志翻出来算了一遍：**9 月 2 日 20:24 短窗还剩 51%，21:07 就已经烧到 96%——43 分钟吃掉将近半个窗口**，中间没干别的，就是改同一个脚本、来回试同一种错。同样的月费，前一天能跑完三件事，这一天连一件都没收尾。

## 二、窗口制这个东西，本身就是反人类的

按时间窗给额度，这个设计的出发点我理解：防滥用、平滑负载。

但它是按**服务器的钟**算的，不是按**我的活**算的。

于是就有了这些场景：

- 我干到一半，最关键的排错环节，窗口没了。等重置。等着的时候我不是在休息，我是在干噎。
- 重置是**滚动**的，不按你的作息走。7 月 28 日 18:02 那一秒，我的短窗用量从 18% 直接掉回 6%——窗口在我干活干到一半的时候自己翻篇了。想攒着明天用？不行，它在你不看的时候悄悄走掉。
- 一层是「短周期的窗口」，一层是「每周总量」，两层叠着算。9 月 11 日我 19:38 开工时短窗 2%、周额度 35%，干到次日 02:27，短窗 94%、周额度 61%——**一个晚上干掉四分之一个周的量**。照这个速度，一周的有效产能只够我认真干三四个晚上；被拦下的时候，我甚至说不清是这两层里的哪一层在拦我。
- 43 天里，短窗峰值突破 85% 的有 5 天。也就是说，只要那天我认真干活，就大概率会撞到墙。

这些数字不是我估的，是 Codex 自己记的：每个会话的 rollout 日志里都有 `rate_limits` 字段，带 `primary` / `secondary` 的 `used_percent` 和 `resets_at`。想看自己的：

```bash
# 会话日志在 ~/.codex 下，把所有额度快照抓出来
grep -rh 'rate_limits' ~/.codex --include='*.jsonl' | python3 -c "
import sys, json
for line in sys.stdin:
    try: d = json.loads(line)
    except Exception: continue
    def walk(o):
        if isinstance(o, dict):
            if isinstance(o.get('rate_limits'), dict):
                yield o['rate_limits']
            for v in o.values(): yield from walk(v)
        elif isinstance(o, list):
            for v in o: yield from walk(v)
    for rl in walk(d):
        p = rl.get('primary') or {}
        if p.get('used_percent') is None:      # 有些快照没有短窗字段，跳过
            continue
        print(d.get('timestamp','')[:19], p['used_percent'], 'reset@', p.get('resets_at'))
"
```

在本机跑出来是 6880 行，时间戳是 UTC，记得 +8 换算；嫌多就在末尾接 `| tail -20`。

CLI 里更省事：会话中直接敲 `/status`，能看到当前哪一层额度快满了。

我的工作节奏是「一件事从想清楚到写完，需要连贯的两三个小时」，不是「每几小时领一次配额，像领饲料一样喂给电脑」。

把这么连续的活儿，切成一段一段的水位线，真的很别扭。

## 三、比限额更糟的是：规则在动

这是我最想吐槽的一点。

订阅制最值钱的东西本来是「可预期」——我知道我一个月有多少，我能据此安排项目。但现在这个可预期性正在被一点点抹掉。

**模型换代，消耗也换代。** 同一个问题、同一个我、同一个订阅，换了新模型之后，一轮对话可能比过去更「贵」。额度没涨，价格没降，能干的活变少了。官方那套「旧模型下线，请切换到新模型」的通知，翻译过来就是：你要么接受更快的消耗，要么别用。前阵子我这边模型列表就动过一次，界面上名字换了，我原本配好的一套东西跟着失效——这类事一年能撞上好几回，而且从来不在我方便的时候发生。

**重置规则像抽奖。** 有时给重置，有时给的是「存入的重置」，还得留意它有有效期；有时是集体重置，所有人一起清零。这套逻辑我完全跟不上。「因为马上要重置了所以赶紧刷掉」这种心态，本身就是设计失败的证据——正常的产品不该让用户觉得，不浪费反而是一种损失。

**促销额度攒不下来。** 送你双倍额度，听起来很大方。但如果我白天在上班、晚上才有空，这份「双倍」有一大半是白给的。我拿到的不是两倍产能，我拿到的是两倍焦虑。

## 四、Grok 那边：池子混着算，更难猜

如果说 Codex 的问题是「窗口太碎」，Grok 这边的问题就是「池子太混」。

我这边是把它当第二个选择用的：Codex 那边卡住了，转过去接着聊。

它的问题跟 Codex 方向相反：Codex 是窗口太碎，Grok 是**池子太混**。官方口径已经不再给「聊天额度」这种单项了——原先聊天、出图、语音、生成这些分开按天计的限额，被并成了一个**跨产品的共享周池**。这不是我听说的，是本机客户端日志里就写着：`USAGE_PERIOD_TYPE_WEEKLY`，一个周期七天。

而且它的周是**锚在 UTC 15:40:40** 翻篇的——换算成北京时间是 **23:40**。不是零点，不是周一早上，也不是我开工的时候。一个从夜里 11 点 40 分开始计的「周」，跟任何人的工作节奏都对不上。

更难受的是这个池子只给百分比，不给你换算。我这边真实记录到的是某周跑到 **68%**，下一分钟就变 68% 卡着不动——**你只能看着一个数字猜自己还能干几件事**。而且配置里 `onDemandCap` 是 0：**额度花完就是硬停**，默认没有「加钱接着跑」这个选项。等一周，或者再买一份别的订阅，你自己挑。

然后是这件事里最荒谬的一层。我把本机 Grok 会话的用量翻了一遍：4 个会话、200 轮对话，**输入累计 3031 万 token，其中 2941 万是缓存重读，占 97%；输出只有 19.7 万，占 0.65%**。

说白了，多轮 agent 每开一轮都要把整个上下文重新发一遍。**额度烧得快，不是因为你干了多少活，是因为它在反复复读。** 你多问一嘴，代价不是那一句话，是你之前所有沉默的上下文再来一遍。

这两个数也能自己查（macOS 上 Grok 客户端把用量写在本机）：

```bash
# 1) 周池周期与真实百分比
grep -o '"creditUsagePercent":[0-9.]*' ~/.grok/logs/unified.jsonl | sort -u
grep -o '"USAGE_PERIOD_TYPE_WEEKLY"' ~/.grok/logs/unified.jsonl | head -1

# 2) 每个会话的累计用量（重点看缓存重读占多少）
python3 - <<'EOF'
import json, pathlib
d = json.loads((pathlib.Path.home()/'.grok/client-state/session-meta.json').read_text())
for sid, m in d.items():
    u = m.get('usage')
    if not u:
        continue
    print(sid[:8], u['numTurns'], '轮  输入', f"{u['inputTokens']:,}",
          ' 缓存重读', f"{u['cachedReadTokens']:,}", ' 输出', f"{u['outputTokens']:,}")
EOF
```

于是我又要开始做算术：这周还剩多少？这段视频值不值得？要不要先留着额度等真正的活？

我不是来用工具的，我是来记账的。

而且两边的规则还不一样。Codex 是「窗口 + 周总量」两层，Grok 是「一个池子大家分」，我还要在脑子里维护两套模型，随时心算自己还剩多少。**每换一个工具，就得重学一套配额规则**——这是订阅制最大的隐形税。

## 五、真正的成本，是被打断

额度用尽这件事，损失的不是那点钱。

是**思路断了**。写到一半被提示拦住，切去另一个工具，上下文要重新交代一遍，语气、约束、项目结构全部重讲。等好不容易接上，原来那股劲儿已经散了。

是**被迫买了第二份订阅**。不是为了更强的能力，只是为了在被卡住的时候有个备胎。这笔钱本来不该花。

是**被迫把活切碎**。为了不浪费额度，我开始把本来一趟能干完的事拆成三趟，中间还要停顿等待——「为了省额度而降低效率」，这听着就荒谬。

## 六、我要的不多，就三条

我不奢求无限，那是做梦。我就要三件事：

1. **把规则说清楚**，说人话。别让我猜什么算重、什么算轻、共享池里到底是谁在吃我的额度。
2. **给我一个能看的用量计**。像手机流量那样，实时告诉我今天用了多少、这个周期还剩多少、什么时候刷新。
3. **别半夜偷偷重置，别让额度凭空作废**。要么按我的周期算，要么让我自己决定什么时候花。

这三条做到了，我一个月多花点钱都行。做不到，那就别怪用户永远在「用完了再骂」和「骂完了续费」之间循环。

## 写在最后

我还是会续费。

因为我确实离不开它，它确实帮我做完了很多活。但这不代表我认可它的额度模式。

我把账算清楚一点：**我买的不是「无限可能」，我买的是一段被窗口切碎、被规则改动、被强制清零的有限产能。** 而卖我东西的人，从来没打算让我事先知道自己买到了多少。

哪天我摁着计算器问自己「这个月到底值不值」，那才是这套模式真正该被反思的时候。
