vibe coding 这个词最近在技术社区里出现的频率明显变高了，V2EX 上有个帖子统计大家现在都用什么方案，回复一百多条。简单说，vibe coding 就是**用自然语言描述需求，让 AI 把代码写出来**，人负责提要求和看结果，不自己一行行敲。

我是被一个小需求逼着开始用的。当时要写个处理表格的小脚本，想着让 AI 全包试试，结果真跑通了。从那以后流程慢慢固定下来，这篇记录一下我现在的工作流，给想试的人一个参考。

## 先选工具：命令行 agent 还是 AI 编辑器

目前主流方案分两类：

1. **命令行 agent**（比如 Claude Code、Codex CLI）：直接在你项目目录里干活，能读文件、改文件、自己跑命令，看到报错自己修。适合已经会用终端的人。
2. **AI 编辑器**（比如 Cursor 这类）：界面里直接跟 AI 聊，改代码实时可见。适合不熟悉命令行的朋友，门槛低一些。

价格方面这两类基本都是订阅制，一般都有免费额度可以先试，具体价格变动快，以官网为准，这里不写死数字。我个人的选择是命令行 agent 为主，因为我能看到它每一步在干什么，心里有底。

## 我的工作流，一共五步

### 第 1 步：把需求写清楚

这一步决定成败。不要只丢一句「帮我写个爬虫」，要把功能点列成清单，明确不要什么。我常用的提示词模板（可以直接复制）：

```text
我要做一个小工具：<一句话说清功能>
使用 <语言/框架>
具体要求：
1. <功能点>
2. <功能点>
3. <功能点>
明确不要做：<避免 AI 自由发挥的部分>
先给我一个实现方案，我确认了再写代码
```

注意最后一句。让 AI 先出方案再动手，能省掉大量返工。

### 第 2 步：先确认方案，再让它写码

很多人跳过这步，结果 AI 一上来就咔咔写，方向错了全白干。让它先把方案列出来，你觉得没问题了，再说一句「按这个方案写」。

### 第 3 步：动手前 git 提交一次干净基线

AI 改代码之前，先把当前状态提交一次：

```bash
git add -A
git commit -m "baseline: 改代码前的干净状态"
```

这样它改坏了随时能回退，这是我最推荐的保险措施。

### 第 4 步：跑起来，报错原样贴给它

写完让它自己运行。报错了不要自己查，把终端里的报错**原样复制**贴给它，说「报错如下，修复它」。AI 看报错改代码非常快，这一步是整个流程里最爽的。

### 第 5 步：小步提交，看 diff 验收

每完成一个功能点就 commit 一次，提交信息写清楚。接受它的修改前，先看一眼 diff：

```bash
git diff
```

大改动一定要问一句「为什么这么改」。别闭眼全盘接受。

## 踩过的坑

- **AI 喜欢一上来就重构整个项目结构**。小需求就明确告诉它「不要动现有文件结构」，不然它会顺手把你的代码重排一遍。
- **上下文会被聊满**。聊久了 AI 会「忘记」开头的要求，特别是关键约束。感觉它开始答非所问，就新开一个会话，把需求重新贴一遍。
- **别让它改自己写的东西太多次**。同一个文件来回改四五轮之后，质量明显下降，不如让它重写。
- **生产环境直接试是最危险的**。先在本地跑通，确认没问题再考虑上线。

## 什么样的人适合用

适合：写小工具、脚本、一次性任务、原型验证——这类活以前要花一晚上的，现在一顿饭的功夫就出来能跑的东西。

不适合：核心业务逻辑、需要严谨审查的代码。AI 写出来如果没人 review，那就是埋雷，这种场合老老实实自己写。
