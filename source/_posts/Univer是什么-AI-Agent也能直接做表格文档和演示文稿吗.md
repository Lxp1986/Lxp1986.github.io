先给结论：**Univer 不是一个“会替你打开 Excel 的聊天机器人”，而是一套可以嵌入应用、让人和 AI Agent 一起处理办公内容的 Office SDK。** 它的价值不只是生成一张表，而是试图把表格、文档、演示文稿、画布、数据表和 Agent 工作流放到同一个可编程环境里。

我今天在 GitHub Trending 里看到 `dream-num/univer`，去看了官方仓库和生态页。这里先不把它写成已经在我电脑上跑通的实测：本文先按官方资料拆定位，再用我熟悉的工程量表、报价书和 PDF 交付场景，说明它真正值得验证的地方。

![Univer 把 AI Agent、Office 内容和结果检查放进同一个工作环境的示意图](/img/univer-agent-office.svg)

## 一、为什么 AI Agent 处理办公文件没有想象中简单

让 Agent 写一段文字很容易，让 Agent 交付一个能用的办公文件，难点就多了：

- 表格公式有没有引用错行；
- 单元格格式有没有被覆盖；
- 合并单元格是否破坏了后续编辑；
- 中文字体和打印边界是否正常；
- 文档里的数字是否与原始数据一致；
- Agent 是否把原文件直接覆盖；
- 修改后能不能比较和回滚。

以一份工程报价书为例，流程不是“生成一个 xlsx”这么简单：

```text
原始工程量数据
  ↓
整理分项和单位
  ↓
写入表格并计算金额
  ↓
生成报价书和说明
  ↓
检查公式、格式、页眉页脚
  ↓
人工复核后交付
```

我以前用 `openpyxl` 和 `python-docx` 做过这类自动化。脚本能生成文件，只说明“文件出现了”，不说明“文件可以交付”。

## 二、Univer 到底是什么

Univer 官方仓库把自己定位为面向 AI Agent 的 Office Harness，同时也是一套高性能、可定制的 Office SDK。

官方仓库列出的能力包括：

- Spreadsheets：表格；
- Documents：文档；
- Presentations：演示文稿；
- Canvas：画布；
- Relational Tables：关系型数据表；
- PDF：官方仓库当前标注为后续能力，不能提前写成已经完整可用。

它的底层思路不是做一个封闭的办公软件，而是提供可以嵌入浏览器或 Node.js 的能力，通过插件架构、公式引擎和统一 Facade API，让其他应用把办公能力接进去。

![Univer 的内容类型和统一 API 关系图](/img/univer-office-layers.svg)

## 三、它和 Excel、WPS、LibreOffice、Python 脚本有什么不同

| 方案 | 主要定位 | 优点 | 局限 |
| --- | --- | --- | --- |
| Excel | 人直接编辑和计算 | 生态成熟，用户熟悉 | Agent 协作和版本审计要另搭 |
| WPS | 桌面/云办公 | 中文办公体验完整 | 自动化接口和部署边界依赖具体产品 |
| LibreOffice | 开源桌面办公 | 可离线、格式能力较完整 | Agent 工作流需要额外封装 |
| openpyxl / python-docx | 脚本生成文件 | 轻量、可复现、适合批量 | 不是真正的交互式 Office 环境 |
| Univer | 可嵌入的 Office SDK / Agent 工作环境 | 表格、文档和 Agent 可放在同一层 | 生态、兼容性和生产成熟度需要实测 |

Univer 不一定要替代 Excel。更现实的用法是：

```text
人负责确认业务规则
Agent 负责整理和生成
Univer 负责承载、编辑、预览和协作
人再负责最终复核
```

## 四、它对 Agent 工作流的意义

### 1. Agent 不只输出文本

传统 Agent 的结果常常是一段 Markdown、一个 JSON 或几条命令。办公场景里，结果必须进入一个人能继续编辑和检查的文件环境。

Univer 的方向是让 Agent 直接操作办公内容，同时保留人在同一工作空间中查看和修正的可能。

### 2. 表格不是字符串拼接

工程量表里有单位、数量、单价、合价、汇总和引用关系。真正可靠的自动化，至少要知道：

```text
哪些是输入
哪些是公式
哪些是人工调整项
哪些是最终输出
```

如果 Agent 只会把结果写进单元格，却没有公式、版本和校验意识，最后仍然需要人工逐格检查。

### 3. 结果检查要进入流程

AI Agent 生成文件后，不能只说“完成了”。应该同时给出：

- 改了哪些工作表；
- 新增了哪些公式；
- 哪些单元格有异常；
- 使用了哪些原始数据；
- 哪些地方需要人工确认；
- 如何回退到上一个版本。

Univer 生态页里提到的 CLI 和 Agent 集成方向，值得关注的正是“创建、检查、交付”这条完整链路，而不是只生成一个漂亮页面。

## 五、结合工程资料，最值得验证的案例

我会用下面这个案例来测，而不是拿一张空白表格演示：

### 输入

```text
渠道清淤工程量 CSV
- 分项名称
- 断面面积
- 渠道长度
- 单位
- 单价
```

### Agent 任务

1. 读取 CSV；
2. 按分项整理工作表；
3. 生成数量、单价和合价公式；
4. 标出缺失数据；
5. 生成汇总页；
6. 导出一份给人审核的结果。

### 必须检查的结果

```text
数量是否等于输入数据
公式是否引用正确
汇总是否等于明细之和
单位是否混乱
小数位是否统一
打印和导出是否正常
```

![工程量数据经过 Agent 整理、校验和人工复核后形成可交付文件的流程](/img/univer-office-workflow.svg)

如果它只能生成表格，不能帮助检查这些关系，那它和一个更复杂的文件生成脚本差别并没有宣传中那么大。

## 六、Univer 的优势和限制

### 可能的优势

- 表格、文档、演示内容可以放在同一套 SDK 思路里；
- 可以嵌入自己的 Web 或 Node.js 应用；
- 比单纯拼接 xlsx 文件更接近交互式办公环境；
- 适合把 Agent 的生成、检查和交付串在一起；
- 官方生态已经开始提供 CLI、技能和 Agent 集成示例。

### 需要冷静看待的限制

- 它不是 Excel 的简单平替；
- 文件格式兼容性需要用真实文件测试；
- Agent 生成的公式和数据仍然可能出错；
- 复杂打印、字体、分页和 PDF 导出不能只看演示；
- 官方仓库标注为 coming soon 的能力不能提前当作现成功能；
- 生产环境还要考虑权限、版本、审计和数据存储。

## 七、它和我现有工具怎么配合

我不认为 Univer 会马上替代我现在的脚本。更现实的组合可能是：

```text
Python / openpyxl
负责数据清理、计算和批处理

Univer
负责可视化编辑、Agent 交互和结果检查

python-docx / PDF 工具
负责最终报价书、说明文件和交付格式
```

也就是说，脚本负责确定性工作，Office Harness 负责交互式工作，Agent 负责理解任务和串联工具，人负责业务判断。

## 八、适合谁，不适合谁

### 适合尝试的人

- 需要让 AI Agent 处理表格和办公文档；
- 正在做工程量、报价书、报表或资料交付自动化；
- 想把 Office 能力嵌入自己的系统；
- 需要让人和 Agent 一起检查文件；
- 接受先做小范围验证，而不是直接替换现有办公软件。

### 暂时不适合的人

- 只需要偶尔生成一个简单 Excel；
- 不想维护 Node.js、前端和插件环境；
- 依赖复杂的既有 Excel 宏和特殊格式；
- 要求所有 PDF 和 Office 格式一次性完全兼容；
- 希望 Agent 生成后完全不需要人工复核。

## 九、我的初步判断

Univer 值得看的地方，不是“AI Agent 终于会做 Office 了”这种口号，而是它试图把办公文件从静态附件变成 Agent 可以操作、检查和交付的工作空间。

但这条路的验收标准不能是：

> Agent 能不能生成一个看起来像表格的文件？

真正要问的是：

> Agent 能不能在不破坏数据、公式、格式和版本的情况下，生成一个人敢继续使用的办公文件？

这也是我后面真正实测时会关注的重点。

## 十、下一步怎么实测

我会先选择一个无敏感数据的工程量表，验证：

1. 安装和启动成本；
2. CSV 或 Excel 数据导入；
3. 公式创建和重新计算；
4. 修改前后版本对比；
5. Agent 能否解释自己改了什么；
6. 表格导出和打印效果；
7. 与 `openpyxl`、`python-docx` 的配合方式。

在完成这些测试前，本文只做定位和方案分析，不提前声称 Univer 已经适合所有办公生产环境。
