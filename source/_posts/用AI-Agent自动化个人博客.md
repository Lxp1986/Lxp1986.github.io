个人博客最大的敌人不是写不好，是**断更**。一开始热情满满，写着写着就停了——因为每篇文章都要自己选题、查资料、排版、发布，太累。

这篇文章不讲"怎么写爆款"，讲一个更实在的问题：**怎么让博客的日常更新不再靠意志力，而靠一套能自动运转的系统。**

我自己就搭了这么一套，跑了挺久，把它拆开讲清楚。

## 一、先解决"发布累"：静态站 + 自动部署

选 **Hexo**（静态博客生成器）+ **GitHub Pages**（免费托管）组合，原因很简单：

- 纯 Markdown 写文章，不碰数据库、不碰服务器；
- 源码放 GitHub 仓库，天然有版本历史，写错了随时回滚；
- 免费、零维护，不用担心服务器挂了。

关键在**自动部署**。本地写好文章，`git push` 一下，剩下的交给 GitHub Actions：自动装依赖 → 构建成静态文件 → 发布到 `gh-pages` 分支。全程一条命令，甚至这一条都能省掉。

`.github/workflows/deploy.yml` 核心就三步：checkout 源码、`npx hexo generate` 构建、把产物推到 gh-pages。配一次，以后每次 push 都自动上线。

## 二、再解决"写什么累"：让 AI 定时生产

发布自动化之后，剩下的痛点就是**内容**。这时候把 AI Agent 接进来。

思路：给 Agent 配一个**定时任务**，每天固定时间自动跑——联网看当下热门话题 → 选题 → 写文章 → 放进 `source/_posts/` → push → Actions 自动上线。人只做一件事：**事后看一眼，质量不行的删掉**。

这里有几个踩过的坑，值得单独说：

1. **提示词要自包含**。定时任务跑在全新会话里，不记得你之前说过什么，所以路径、格式要求、发布步骤都得写进任务描述里，不能省略。
2. **事实必须查证**。让 AI 联网写，最怕它编数据。铁律：涉及价格、版本、事实的，查得到才写，查不到就模糊化，绝不硬编。
3. **本地只 push 源码**。别用 `hexo deploy`，那会全量覆盖 gh-pages，本地落后远程时容易丢内容。交给 Actions 构建发布最安全。

## 三、评论系统选 giscus：数据留在自己手里

博客要不要评论？要，但别用别人的公共示例服务——那等于把评论区数据交给别人管。

选 **giscus**：基于 GitHub Discussions，评论直接存在你仓库的讨论区里。零成本、零服务器，数据归你自己，还能自动给参与讨论的人发通知。配一次，以后不用管。

## 四、复现性：换电脑也要能无缝接管

整套系统最容易被忽略的一点：**能不能复现**。别把关键路径、操作步骤只记在脑子里，哪天换电脑、换 Agent，就接不上手了。

我的做法：写一份**总控手册**，把仓库地址、本地路径、接入步骤、写文 SOP、发布 SOP 全列进去。任何一台新设备上的 Agent，读这份手册就能接手，不用重新摸索。

## 总结

| 环节 | 方案 | 成本 |
|---|---|---|
| 托管 | Hexo + GitHub Pages | 免费 |
| 部署 | GitHub Actions | 免费 |
| 内容 | AI Agent 定时生产 | 低价 API，一天几块钱 |
| 评论 | giscus + GitHub Discussions | 免费 |
| 复现 | 总控手册 + GitHub 仓库 | 免费 |

一句话：**把博客从"靠人写"变成"靠系统跑"，人只做选题把关和质量审核。** 断更这个问题，就被架构解决掉了。
