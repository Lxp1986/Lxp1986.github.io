先给结论：**Docker Cloud Sandboxes 解决的不是“让 AI 更聪明”，而是让 Agent 执行任务时少碰一点不该碰的东西。** 当 Agent 需要读文件、装依赖、跑命令、改代码甚至访问网络时，把它直接放在自己的主机上并不理想；云端隔离环境至少把“执行地点、工具、权限和生命周期”单独拎了出来。

Docker 在 2026 年 9 月 24 日的官方公告中，把 Cloud Sandboxes 定位为面向复杂 Agent 工作流的隔离执行环境，并同时介绍了新一代 Kits：把 Agent、工具和访问规则作为标准 OCI 镜像来打包。这个方向值得关注，但我先把边界说清楚：**本文是官方资料核对和工程角度的拆解，不把没有亲自跑过的部署过程写成实测。**

![Docker Cloud Sandboxes 将 Agent、工具和权限规则放进隔离执行环境的示意图](/img/docker-cloud-sandbox.svg)

## 一、为什么 Agent 需要沙箱

普通聊天不需要沙箱。你问一句，模型回一句，最多是内容答错。

Agent 不一样。一个能调用工具的 Agent，可能会经历这样的链路：

```text
收到任务
  ↓
读取项目文件
  ↓
安装依赖
  ↓
执行脚本和测试
  ↓
修改代码或生成文件
  ↓
访问网络/API
  ↓
返回结果
```

这条链路里，风险不只来自模型本身，也来自工具权限和运行环境：

- Agent 可能把本地密钥当成普通配置读出来；
- 安装依赖时可能执行第三方安装脚本；
- 测试脚本可能误删目录或覆盖文件；
- 网络访问可能把数据发到不该去的地址；
- 失败重试可能重复产生费用或副作用；
- 一个看似普通的任务可能间接触碰生产环境。

所以“给 Agent 一个终端”与“给 Agent 一个隔离的执行环境”不是一回事。

## 二、Docker Cloud Sandboxes 是什么

根据 Docker 的官方公告，Cloud Sandboxes 是云端提供的隔离运行环境，目标是让复杂的 Agent 工作流可以在开发者电脑之外继续运行，不必把整台电脑一直开着，也不必直接把 Agent 放进本机生产环境。

可以先把它理解成四个部分：

| 部分 | 作用 |
| --- | --- |
| Agent | 负责理解目标、规划和调用工具 |
| Tools | 终端、代码执行、浏览器或其他工作工具 |
| Rules | 规定能访问什么、不能访问什么 |
| Sandbox | 提供隔离的文件系统、进程和运行生命周期 |

![Agent 沙箱的四层结构：模型、工具、权限规则和隔离环境](/img/docker-sandbox-layers.svg)

它的重点不是再提供一个远程 Linux 主机，而是把 Agent 执行时需要的东西一起封装，尽量避免“模型在云端，工具却偷偷连回你的电脑”这种边界不清的情况。

## 三、它和普通 Docker 有什么区别

Docker 容器本身不是安全魔法。容器怎么启动、挂载什么目录、给了哪些 capability、网络是否开放，都会影响最终的隔离程度。

### 普通 Docker 更像一个本地工具

本地 Docker 适合：

- 在自己的电脑上跑开发环境；
- 固定依赖和版本；
- 做构建、测试和服务编排；
- 用 compose 管理几个相互依赖的容器。

但如果你把下面这些东西直接暴露给 Agent：

```text
/Users/你的用户名
SSH 私钥
云服务凭证
生产环境配置
Docker socket
```

那么“进了容器”不代表风险自动消失。

### Cloud Sandboxes 更强调 Agent 的运行边界

Docker 官方公告把 Cloud Sandboxes 放在 Agent 工作流背景下讨论，重点是让 Agent 工作在独立、可重复、可销毁的云端环境里。

换句话说：

```text
普通 Docker：我怎样把程序跑起来？
Cloud Sandbox：我怎样让 Agent 在受控边界里完成任务？
```

两者不是互相替代，而是关注层次不同。

## 四、Docker 官方提到的 Kits 是什么

公告中另一个值得注意的部分是新一代 Kits。

官方给出的方向可以概括为：

```text
Agent
+ 工具
+ 执行规则
+ 运行环境
= 可共享的 OCI artifact
```

这比单独给一个 Dockerfile 更接近 Agent 的真实交付方式。因为一个 Agent 能不能稳定工作，往往不只取决于代码，还取决于：

- 它能使用哪些工具；
- 工具以什么身份运行；
- 能读写哪些路径；
- 能访问哪些网络地址；
- 任务结束后哪些文件需要保留；
- 出错时如何清理和恢复。

如果这些内容都能和运行环境一起打包，就更容易在不同机器和团队之间复现。

但这里仍然要避免误解：**OCI 镜像解决的是交付和复现，不等于自动解决所有安全问题。** 镜像里如果自带危险脚本，或者运行时仍然挂载了过大的权限，封装得再漂亮也没有用。

## 五、Cloud Sandbox、本地 Docker 和本机直接执行怎么选

| 方式 | 优点 | 主要风险 | 更适合 |
| --- | --- | --- | --- |
| 本机直接执行 | 最方便，访问本地资源最快 | Agent 直接碰到主机和密钥 | 可信、短小、人工盯着的任务 |
| 本地 Docker | 成本低，环境可复现 | 挂载和权限配置容易过宽 | 开发、测试、离线实验 |
| 云端沙箱 | 与个人电脑隔离，可跑长任务 | 云端凭证、网络和成本需要管理 | 多 Agent、远程执行、复杂任务 |
| 传统云主机 | 自由度高，长期服务方便 | 隔离边界大多靠自己搭 | 有运维能力的长期服务 |

我自己的判断是：只要任务包含“自动执行代码 + 网络访问 + 第三方依赖”其中两项，就不应该默认让它直接跑在主机上。

## 六、它和 Paperclip、Codex、Hermes 是什么关系

我刚发布的 Paperclip 文章讨论的是 Agent 的组织、目标、任务、预算和治理。Docker Cloud Sandboxes 讨论的是 Agent 在哪里执行，以及执行时能碰什么。

可以按层次理解：

```text
Paperclip
目标、组织、任务、预算和治理
        ↓
Codex / Hermes / Claude Code 等
Agent 的规划、对话和工具调用
        ↓
Docker Cloud Sandboxes
隔离的执行环境和工具包
        ↓
云端基础设施
计算、存储、网络和凭证
```

![Paperclip、Agent 运行时和 Docker Cloud Sandbox 的层级关系](/img/docker-agent-stack.svg)

这也是我认为这个话题比单纯介绍 Docker 新产品更有价值的原因：**Agent 组织层和 Agent 执行隔离层，迟早要同时考虑。**

## 七、接入真实工作流前要检查什么

### 1. 文件边界

先问清楚沙箱能看到什么：

- 是否默认有 home 目录；
- 是否能访问项目外的路径；
- 任务结束后文件是否自动销毁；
- 输出文件如何取回；
- 临时文件和缓存保存多久。

### 2. 凭证边界

不要把整套生产密钥直接塞进 Agent 环境。更稳妥的做法是：

- 用最小权限的临时凭证；
- 区分读权限和写权限；
- 给不同任务不同的 API Key；
- 明确凭证是否会进入日志；
- 任务结束后撤销或过期。

### 3. 网络边界

“能访问互联网”是一个很大的权限。至少要核对：

- 是否可以限制域名；
- 是否可以关闭出站网络；
- DNS 和代理由谁控制；
- 下载的依赖是否可追踪；
- 任务结果是否会发送到第三方服务。

### 4. 成本边界

云端沙箱让电脑可以关机，但不代表运行免费：

- 任务运行多久；
- CPU、内存和存储怎么计费；
- Agent 失败后是否自动重试；
- 多个 Agent 是否会同时创建沙箱；
- 沙箱是否会因为忘记销毁持续产生费用。

### 5. 退出和审计

真正接入生产前，必须知道：

- 如何暂停正在运行的任务；
- 如何撤销某个 Agent 的权限；
- 如何查看完整命令和工具调用日志；
- 如何导出结果和审计记录；
- 云服务故障时能否恢复工作。

## 八、它适合谁

### 适合

- 已经在使用多个 Agent；
- 需要让 Agent 跑长任务；
- 不想让 Agent 直接进入个人电脑；
- 有重复创建和销毁执行环境的需求；
- 需要把 Agent、工具和权限规则一起交付；
- 愿意管理云端成本和凭证。

### 不适合

- 只是偶尔和模型聊天；
- 任务完全不需要执行代码；
- 没有任何权限和成本控制方案；
- 希望部署后就把生产密钥全部交给 Agent；
- 不愿意查看日志和处理失败任务。

## 九、我的初步判断

Docker Cloud Sandboxes 反映了一个变化：**Agent 产品的竞争已经从“谁能回答得更好”逐渐延伸到“谁能把任务安全地跑完”。**

模型、工具、环境和权限必须一起设计。只增加一个更强的模型，不能自动解决：

- 文件会不会被误读；
- 命令会不会误执行；
- 密钥会不会泄露；
- 重试会不会失控；
- 费用会不会超预算。

Cloud Sandbox 是一个合理的工程方向，但它不是安全许可证。最后的风险仍然取决于你给了多少权限、挂载了什么数据、开放了哪些网络，以及有没有人工停止和审计机制。

对我来说，比较稳妥的使用顺序是：

```text
先在无敏感数据环境试跑
  ↓
限制文件、网络和凭证
  ↓
观察日志、成本和失败重试
  ↓
再接入真实项目
```

## 十、下一步怎么实测

如果继续研究，我会用一个没有敏感数据的测试仓库，比较三种方案：

1. 本机直接跑 Agent；
2. 本地 Docker 运行 Agent；
3. Docker Cloud Sandbox 运行同一个任务。

测试指标包括：

- 启动时间；
- 依赖安装时间；
- 文件隔离效果；
- 网络限制方式；
- 任务失败后的清理；
- 日志完整程度；
- 实际费用；
- 是否容易接回 Git 和现有工作流。

在完成这组测试之前，我不会把 Cloud Sandboxes 写成“最安全”或“最便宜”的方案。
