一个 agent 不够用了：多 agent 怎么分工才不打架

发表于2026-10-04|更新于2026-10-09|AI工具
|浏览量:|评论数:

先给结论：多 agent 翻车的根因从来不是”agent 太多”，而是没分工。 一人干所有事，上下文撑爆、任务互相串；拆成三五个人却不设边界，照样打架。分工、隔离、验收三件事做到位，数量不是问题。

什么时候该从一个拆成多个

三个信号，出现任意一个就该拆：

信号 症状
任务可并行 三件事互相不依赖，排队等一个 agent 做纯属浪费时间
上下文超载 对话越来越长，agent 开始遗忘早前的要求、重复问你
需要第二双眼睛 写代码的 agent 自己 review 自己的代码，等于没 review

反过来：如果任务本身很小、一步就能做完，别拆。协调三个 agent 的成本比你自己动手还高。

三种分工模式

这是我调研了本周 GitHub trending 上的多 agent 项目后，提炼出的三种主流分法（核对日期 2026-10-04）：

模式 你怎么指挥 代表项目 适合场景
船长-水手式 你只跟一个 agent 说话，它去派活、盯进度 firstmate（kunchenguid/firstmate，7.5k star） 你不想当监工，只想说人话下命令
固定班子式 用配置文件定义好团队和角色，一键拉起 openrig（mvschwarz/openrig，4.8k star） 长期项目，同一套分工反复用
一次性并行 一个任务拆 N 份，并行跑完即散 各类 swarm / 并行派单工具 赶工：比如同时改 5 个互不相关的 bug

firstmate 的思路最直白：你当船长，只跟大副（first mate）说话；大副给每个水手（crew）开一个干净的 git worktree，活干完交 PR 或者调查报告，你只负责拍板。openrig 则更像组建固定团队：用 YAML 写好谁是 owner、谁是 checker，Claude Code 和 Codex 可以在同一个团队里混编，团队长期存在、上下文不断。

工具会换，但这三种模式背后的分工逻辑这几年一直没变。

不打架的三条铁律

这是我自己带多个专门 subagent 干活时总结的，工具无关：

1. 隔离：每人一个干净的工作区。

多个 agent 绝对不能共用同一个工作目录。firstmate 给每个任务开独立 git worktree 就是这个道理——代码层面的隔离，冲突在合并时才暴露，而不是在干活时互相覆盖。非代码任务也一样：每人一份独立的输入材料和输出位置。

2. 边界：先划清只读和可写。

动手之前说清楚：谁可以改文件，谁只能读、只能出报告。firstmate 默认大副对项目只读，改动全走水手提交的 PR，由你批准才合并。权限这事宁可一开始紧一点，也别等出事了再收。

3. 验收：每个子任务有明确的完成标准。

派活时不说”把登录 bug 修一下”，而说”修好登录 bug，测试通过，把改了哪几个文件、怎么验证的写清楚，回来找我确认”。子 agent 汇报格式固定，你验收只看三样：做了什么、怎么证明是对的、有没有副作用。标准模糊，返工就多。

最小可用的起手式

不用装任何工具，今天就能试：

  1. 开三个会话：一个当”拆任务+验收”的，一个当执行 A，一个当执行 B。
  2. 给两个执行者一人一份独立任务，明确说”你的输出写到某某文件，别碰别人的”。
  3. 执行完回来找验收者（或者你自己）对：改了什么、测试过没过。

跑通一次，你就知道自己的任务适不适合多 agent。适合，再去研究 firstmate、openrig 这类工具；不适合，说明你的任务本来就该一个人干。

我的判断

多 agent 是手段，不是目的。我见过最多的浪费是反过来的：任务明明 10 分钟能做完，非要摆出三军阵仗，最后协调成本吃掉所有收益。

另外一个判断：验收标准的质量，决定多 agent 的上限。 分工可以抄工具的，隔离可以用 worktree 解决，但”什么叫干完了”只能你自己定义清楚。定义不清楚，派出去的 agent 越多，回来返工的也越多。
