先把话说在前面：我不是嫌贵。

我一个月掏的那点钱，换来一个能读我仓库、能替我敲命令、还能帮我改脚本的东西，这笔账怎么算都不亏。我甚至愿意多花点。

我别扭的是这个：**钱是按月收的，额度却是按 5 小时、按周给的。**

![钱按月付，额度按周期切碎：一边是平地，一边是锯齿](/img/ai-sub-quota.svg)

## 一、模式上的错配：钱按月，额度按天

订阅制听着像包月。真用起来，你手上其实是一叠周期券：一个 5 小时窗，一周的量，或者干脆全部产品共用一个周池。

问题出在两头都对不上。

忙的那几天，一个下午就能把短窗烧到见底，剩下的时间只能等。闲的那几天——比如出差、开会、陪家里人——额度该过期的照样过期。**你不用的部分不会攒下来，也不会退你钱。** 用的时候不够，不用的时候浪费，这两件事同时成立。

说它像包月，是抬举它了。真包月是「随便用」，它更像「按月买一堆会用过期的小票」。

## 二、Codex：一层 5 小时窗，一层周总量

Codex 的额度是两层叠着算的：短的一层按 5 小时滚动，长的一层按周。被拦下的时候，我经常说不清是哪一层在拦我，只能去敲 `/status` 看。

下面这些数是我自己算的，来源是 Codex 写在 `~/.codex` 下的会话日志。43 天，6880 个额度采样点。

- 9 月 2 日，20:24 短窗还剩 51%，21:07 已经 96%。**43 分钟吃掉将近半个窗口**，中间就是改同一个脚本、来回试同一种错。
- 9 月 11 日 19:38 开工时短窗 2%、周额度 35%；干到次日 02:27，短窗 94%、周额度 61%。一个晚上用掉四分之一个周的量。
- 43 天里，短窗峰值超过 85% 的有 5 天。

还有一件我一开始想错了的事。我以为重置发生在固定的时间，比如半夜。日志不支持这个说法：7 月 28 日 18:02 那一秒，短窗用量从 18% 掉回 6%，窗口是在我干活干到一半的时候滚过去重启的。它不是「到点刷新」，而是「一直往前滚」，所以你永远算不准自己还剩多少。

想自己看的话：

```bash
# 会话日志在 ~/.codex 下，把所有额度快照抓出来
grep -rh 'rate_limits' ~/.codex --include='*.jsonl' | python3 -c "
import sys, json
for line in sys.stdin:
    try: d = json.loads(line)
    except Exception: continue
    def walk(o):
        if isinstance(o, dict):
            if isinstance(o.get('rate_limits'), dict):
                yield o['rate_limits']
            for v in o.values(): yield from walk(v)
        elif isinstance(o, list):
            for v in o: yield from walk(v)
    for rl in walk(d):
        p = rl.get('primary') or {}
        if p.get('used_percent') is None:      # 有些快照没有短窗字段，跳过
            continue
        print(d.get('timestamp','')[:19], p['used_percent'], 'reset@', p.get('resets_at'))
"
```

我这边跑出来是 6880 行，时间戳是 UTC，看的时候记得 +8。

## 三、Grok CLI：一个周池，一个百分比，锚点在半夜

这里要先分清两个东西，我自己之前就混过：

- **Grok** 是 xAI 的产品，跟着订阅走的还有一个终端 agent（`~/.grok`，官方的 Grok CLI）。我下面说的数据都属于它。
- **Grok Bot** 是另一家的桌面应用（Anysphere，也就是做 Cursor 那家）。我把它本机的数据翻了一遍，没有找到任何额度字段，所以这一篇里我不对它下结论。

Grok CLI 的额度按周算。这一点不用猜，日志里就写着 `USAGE_PERIOD_TYPE_WEEKLY`，一个周期七天。周期的锚点在 UTC 15:40:40，换成北京时间是 **23:40**。不是零点，不是周一早上，也不是我坐下来干活的时候。

它给你的是一个百分比。我在日志里抓到的值是 10% 和 66%→68%。也就是说你手上只有一个数字，没有别的：出图吃多少、聊天吃多少、语音吃多少，本机数据里**没有任何分项**。数字掉得快的时候，你连该怪什么都没法定位。

至于用完了能不能接着用——我一开始写成「硬停」，这是我的错。事实是：按需追加这件事是存在的，但规则不透明。配置里能看到 `onDemandCap`、`onDemandUsed`、`prepaidBalance` 这几个字段，值都是 0，而账号又被标成「统一计费」。到底追加怎么触发、按什么单价算、扣减顺序是什么，页面上没有一处讲清楚。**你以为能加，但你不确定加了会扣多少——这种不确定本身就够难受了。**

顺便说一个我觉得更值得讲的发现。我把本机 Grok CLI 的会话用量统计了一下：4 个会话、200 轮，输入累计 3031 万 token，其中 2941 万是缓存重读，占 97%，输出只有 19.7 万，占 0.65%。

原因不难理解：多轮 agent 每开一轮，都要把前面的上下文重新发一遍。所以额度掉得快，很多时候不是因为你在干活，而是因为它在复读。你多问一句，代价不是那一句话，是你之前所有沉默的上下文再来一遍。

这两个数也能自己查：

```bash
# 1) 周池周期与真实百分比
grep -o '"creditUsagePercent":[0-9.]*' ~/.grok/logs/unified.jsonl | sort -u
grep -o '"USAGE_PERIOD_TYPE_WEEKLY"' ~/.grok/logs/unified.jsonl | head -1

# 2) 每个会话的累计用量（重点看缓存重读占多少）
python3 - <<'EOF'
import json, pathlib
d = json.loads((pathlib.Path.home()/'.grok/client-state/session-meta.json').read_text())
for sid, m in d.items():
    u = m.get('usage')
    if not u:
        continue
    print(sid[:8], u['numTurns'], '轮  输入', f"{u['inputTokens']:,}",
          ' 缓存重读', f"{u['cachedReadTokens']:,}", ' 输出', f"{u['outputTokens']:,}")
EOF
```

## 四、Cursor：按月算是加分项，可限流来得没道理

我一直在用 Cursor。它有一点比上面两家好：**额度是按月算的**，不是一个下午就归零的窗口。你可以自己安排这个月怎么花，这是正常的包月思路。

但它有另一个毛病：在 IDE 模式里，有时候会突然限流。不是用满了，是莫名其妙就卡住了，等一会儿又好了，也没个提示说为什么。你说它是高峰保护也好、是防滥用也好，反正用户这边只看到一个结论——**不知道自己在什么情况下会被拦。**

规则不可见这件事，比额度少一点更让人难受。额度少，我少干点；规则看不见，我连计划都做不了。

## 五、真正贵的地方，是被打断

额度用尽的损失不在那点钱上。

写到一半被拦住，思路就断了。换个工具接着说，上下文要重新交代一遍，语气、约束、项目结构全得重讲，等接上了，劲儿也散了。

再就是被迫存额度。到了周后期，我会不自觉地想「这个先别动，等下周再说」，明明有空、有想法，却不舍得用。为了省额度而挑活儿干，这听着就不太对。

## 六、我想要的其实不多

1. 规则写清楚：什么算重、什么算轻、共用池里是谁在吃我的量、追加额度怎么算钱。
2. 给一个像手机流量那样的用量计：今天用了多少，这个周期还剩多少，什么时候刷新。
3. 别让周期额度白白作废。要么按我的节奏算，要么让我自己决定什么时候花。

这三条做到，我一个月多掏点钱都行。

## 写在最后

我还是会续费。它确实帮我干完了很多活。

但我不想再为了「今天能不能把活干完」去做算术。付款方式是按月的，那额度也该按月给我一个能安排的数，而不是塞给我一堆会过期的小票，还让我猜哪一张先用完。

哪天我对着计算器问自己「这个月值不值」，那就是这套计费最该改的时候。
